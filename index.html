CASE 1

회사별 비동기 처리 결과와 부분 실패 대응

문제 상황

여러 회사의 전자신고를 한 번에 실행할 때 외부 기관의 처리 시간과 성공 여부가 회사마다 달랐습니다. 각 신고 단계가 이전 단계의 결과에 의존하는 구조여서, 일부 회사가 실패하더라도 나머지 회사의 신고는 계속 진행할 수 있어야 했습니다.

해결 과정
  • 사내 Long Polling 공통 모듈로 회사별 비동기 처리 결과를 수신했습니다.
  • 응답 데이터에서 성공한 회사 ID를 추출해 다음 단계 API의 요청 대상으로 전달했습니다.
  • 실패한 회사는 후속 처리에서 제외하되, 결과 화면에 유지했습니다.
  • 단계별 처리 대상과 성공·실패 결과를 기준으로 진행 상태를 갱신했습니다.
결과

일부 회사의 신고가 실패하더라도 성공한 회사의 후속 작업은 중단 없이 진행할 수 있도록 구현했습니다.



CASE 2

실제 신고가 불가능한 환경에서 테스트 시나리오 구성

문제 상황

개발 환경에서는 홈택스·위택스에 실제 신고할 수 없어, 외부 기관의 처리 결과와 회사별 성공·실패 상황을 재현하기 어려웠습니다.

해결 과정
  • 백엔드 개발자와 Long Polling 응답 데이터 형식을 협의하고 테스트용 API 개발을 요청했습니다.
  • Postman으로 회사별 성공·실패 결과를 지정해 다양한 처리 상황을 재현했습니다.
  • 일부 회사만 성공하는 시나리오를 통해 후속 API 호출 대상과 실패 회사의 처리 제외 여부를 검증했습니다.
  • 백엔드 개발자와 협의해 테스트용 Long Polling 응답 API를 요청하고, Postman으로 회사별 성공·실패 결과를 지정해 처리 상황을 재현했습니다.
  • 일부 회사만 성공하는 시나리오로 후속 API 호출 대상과 처리 제외 여부를 검증했습니다.
결과

실제 신고 없이도 회사별 성공·실패 상황을 재현하고, 단계별 비동기 처리 로직을 검증할 수 있는 테스트 방법을 마련했습니다.

문제 상황

결과

문제 상황

해결 과정

  • 현재 탭의 상태와 저장된 최신 상태를 비교하여, 이전 상태로 열린 탭의 입력·마감 동작을 제한하고 안내 메시지를 표시했습니다.
결과

동일한 신고서를 여러 탭에서 작업할 때 이전 상태를 기준으로 데이터를 변경하는 상황을 방지하도록 구현했습니다.

전자문서지갑 기능을 신규 개발하면서 인증 결과와 전자문서 조회·반영에 필요한 상태를 관리해야 했습니다. 기존에는 앱 인증과 화면 이동 등 여러 기능의 상태를 하나의 Context에서 관리하고 있어, 새로운 기능의 상태까지 추가하면 Context의 역할이 더욱 복잡해지는 구조였습니다.

개선 과정
  • 기존 Context에서 관리하던 상태와 함수를 역할별로 구분했습니다.
  • 인증·브릿지, 화면 이동, 전자문서지갑 관련 상태를 각각 별도의 Context로 분리했습니다.
  • 각 컴포넌트가 필요한 Context를 참조하도록 변경했습니다.
  • 기존 Context에서 관리하던 상태와 함수를 역할별로 구분해 인증·브릿지, 화면 이동, 전자문서지갑 Context로 분리했습니다.
  • 각 컴포넌트가 필요한 Context를 참조하도록 변경했습니다.

문제 상황

전체 수임처·개별 수임처·나하고 대시보드는 서로 다른 정보를 표시하지만, 고객사 선택과 업무 진행 상태 등 일부 데이터를 공유해야 했습니다.

또한 추천 업무 유형에 따라 표시할 데이터와 테이블 컬럼, 실행 가능한 기능이 달라져 이를 일관되게 관리할 구조가 필요했습니다.

전체·개별·나하고 대시보드는 서로 다른 정보를 표시하지만 고객사 선택과 업무 진행 상태 등 일부 데이터를 공유해야 했고, 추천 업무 유형에 따라 표시 데이터·테이블 컬럼·실행 기능이 달라져 이를 일관되게 관리할 구조가 필요했습니다.

해결 과정

1. 공유 상태와 화면 내부 상태 구분

  • 고객사 선택 등 여러 대시보드에서 사용하는 상태는 상위 컨테이너에서 관리하고, 태그 선택과 로딩 등 개별 화면의 상태는 각 컴포넌트에서 관리했습니다.
  • 공통 상태와 변경 콜백을 props로 전달해 각 컴포넌트가 동일한 상태를 기준으로 동작하도록 구성했습니다.

2. 선택 상태에 따른 데이터 갱신

  • 고객사 변경 시 관련 데이터를 다시 조회하고, 변경된 고객사에 맞게 화면 정보를 갱신했습니다.
  • 추천 업무 태그 변경 시 기존 API 응답을 재사용하고, 업무 유형에 해당하는 데이터를 필터링해 별도의 API 재호출 없이 화면을 갱신했습니다.
  • 전체 대시보드에서 선택한 업무 유형을 개별 대시보드로 전달해 화면 전환 후에도 동일한 업무를 확인할 수 있도록 구현했습니다.

3. 업무 유형별 동적 테이블 구성

  • 업무 유형을 기준으로 테이블 헤더·컬럼 너비·셀 데이터·버튼 동작을 매핑했습니다.
  • 공통 Table·TableItem 컴포넌트를 활용해 수임처 단위와 근로자 단위의 데이터를 표시했습니다.
  • 스크롤바 유무에 따른 헤더와 본문 간 컬럼 너비 차이를 보정해 테이블 정렬을 유지했습니다.
  • 고객사 선택 등 여러 대시보드가 공유하는 상태는 상위 컨테이너에서, 태그 선택과 같은 화면별 상태는 개별 컴포넌트에서 관리하도록 구분했습니다.
  • 고객사가 바뀌면 관련 데이터를 API로 다시 조회하고, 업무 유형(태그)만 바뀔 때는 기존 응답을 재사용해 필요한 데이터만 필터링하도록 구성했습니다.
  • 업무 유형별 테이블 헤더·컬럼 너비·버튼 동작을 매핑해 공통 Table 컴포넌트에서 재사용하도록 구성했습니다.

해결 과정

1. 회계 데이터 분류 및 한도 계산

  • 여러 손익계정의 회계 데이터를 적요코드와 신용카드 사용 여부에 따라 지출 유형별로 분류했습니다.
  • 중소기업 여부와 특수관계인 거래금액 등 회사 조건을 반영해 기업업무추진비 한도를 계산하도록 구현했습니다.

2. 계산 로직 공통화 및 재계산 흐름 분리

  • 화면에 분산되어 있던 초기화·금액 반영·계산·합계 처리 로직을 공통 모듈로 분리했습니다.
  • 사용자 입력과 AI 자료 반영 과정에서 동일한 계산 로직을 사용하도록 구성했습니다.
  • 새로운 데이터를 반영하는 경우와 기존 입력값을 기준으로 재계산하는 경우를 구분했습니다.
  • 재계산 시에는 데이터를 다시 불러오지 않고 현재 화면에 저장된 데이터를 활용해 사용자 입력값을 유지하도록 처리했습니다.

  • 화면에 분산되어 있던 초기화·금액 반영·계산·합계 처리 로직을 공통 모듈로 분리해 사용자 입력과 AI 자료 반영에 동일한 계산 로직을 사용하도록 구성하고, 재계산 시에는 현재 화면의 데이터를 활용해 사용자 입력값을 유지하도록 처리했습니다.
